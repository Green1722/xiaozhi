## 硬件与云端共用的数据约定

控制台模型已保存 3 个只读（由设备上报）属性：

| 属性 | 数据类型 | 单位 / 约定 |
| --- | --- | --- |
| `height_cm` | decimal | cm |
| `weight_kg` | decimal | kg |
| `record_id` | string，长度 128 | 同一次测量重传保持不变；新测量使用新编号 |

数值属性当前保留平台默认取值范围 0～65535，这只是接入配置，不代表传感器量程、医学有效范围或业务校验标准。业务 API 的输入校验仍需保留。

上报主题：`$oc/devices/{device_id}/sys/properties/report`

下例是**模拟数据**，不是受检者测量结果：

```json
{"services":[{"service_id":"PhysicalExam","properties":{"record_id":"synthetic-example-001","height_cm":175.0,"weight_kg":70.0}}]}
```

设备端不上传姓名或手机号；云端按身高、体重重新计算 BMI。当前模型没有把 `source`、采集时间做成属性：测试设备与真实设备必须分开登记来源；正式历史记录接入前应补齐采集时间规则，避免用接收时间冒充测量时间。IoTDA 设备影子只保留最新状态，不能当作完整体检历史库。

## 三人交叉与必须先后

1. 云端负责人：恢复测试凭证 → 模拟鉴权及上报 → 控制台核对属性 → 配置业务数据转发及历史入库。这是当前优先链。
2. 测量板负责人：现在可以核查现有固件、测量稳定性及记录编号生成；拿到独立设备凭证后再改接入地址、TLS 认证和上报封装。**未核实板型、SDK和目标前不修改或烧写固件。**
3. 小智负责人：现在可以梳理查询与播报逻辑；联调时按记录编号查询就绪的数据后才触发播报，并区分“已请求”与“实机已播完”。
4. 三人联合：真实测量 → IoTDA → 业务入库 → 按同一记录编号播报；再做断网、重传、重复记录、连续两次测量与设备重启测试。

## 还差什么

- **接入认证**：有效测试密钥、MQTT CONNACK 与 PUBACK、控制台同编号数据证据。
- **业务云端**：IoTDA 到体检 API 的受认证转发、历史保存和部署稳定性；真实 RDS/Redis/MaaS 调用目前没有证据，不写成已实现。
- **成果归档**：取回码道补传队列归档，审阅合并并本地重测；不能用空 patch 代替完整源代码差异。
- **硬件闭环**：真实板卡接入、同编号播报、断网补传与重复记录验证；目前无实机验收。
- **参赛材料**：按初赛必交 Word 模板更新实测结果、真实云产品使用证据及创新价值；初赛可选 PPT、视频不列为阻塞项。
